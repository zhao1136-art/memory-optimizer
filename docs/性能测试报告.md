# MemOptimizer · 性能测试报告

> 版本：v1.0 ｜ 测试日期：2026-08-29

---

## 一、测试目的

验证 MemOptimizer（纯 C 原生内存优化工具）在真实环境下的性能表现，重点评估：
1. **工具自身资源开销**：CPU 占用、内存占用、句柄/线程数，确认"低开销"设计目标；
2. **API 延迟**：各 REST 端点的端到端响应时间；
3. **API 吞吐**：连续请求的处理能力；
4. **功能正确性**：核心功能与 CLI 模式运行验证。

---

## 二、测试环境

| 项目 | 值 |
|---|---|
| 操作系统 | Windows 10 企业版（64 位） |
| CPU | 4 逻辑处理器 |
| 物理内存 | 4040 MB（约 4 GB） |
| 测试时可用内存 | 约 481 ~ 590 MB（**内存较紧张**，后台存在多个常驻进程） |
| 工具版本 | bin\memtool.exe（含 2026-08-29 修复，gcc 16.1.0 -O2 构建） |
| 运行参数 | `--serve --config ..\memtool.conf`（interval 2000ms，window 600，data_dir=data） |
| 采样规模 | 全量进程约 145 个 |

> 说明：测试机物理内存仅 4 GB 且可用内存长期低于 600 MB，属于**高内存压力环境**。此环境下测得的工具自身内存占用仍处于低位，更能体现工具的低开销特性。

---

## 三、测试方法

1. **工具自身资源**：启动服务并静置 90 秒，每 30 秒用 `Get-Process` 采样一次，共 3 次。CPU 使用率 = 相邻两次累计 CPU 时间差 ÷ 时间差；内存取工作集（WorkingSet64）与私有字节（PrivateMemorySize64）。
2. **API 延迟**：对 8 个端点各请求 5 次，用 `Stopwatch` 记录端到端耗时，统计最小/平均/最大。客户端为 PowerShell `Invoke-WebRequest`（含客户端开销）。
3. **API 吞吐**：对 overview 与 processes 端点串行连续请求 50 次，统计每秒请求数（req/s）。
4. **功能验证**：`--snapshot` 与 `--report html` CLI 模式运行，检查输出。

---

## 四、测试结果

### 4.1 工具自身资源占用（静置 90s）

| 采样轮次 | 工作集 (MB) | 私有内存 (MB) | CPU (%) | 句柄 | 线程 |
|---|---|---|---|---|---|
| 第 1 轮（30s） | 8.90 | 5.34 | 0.000 | 61 | 3 |
| 第 2 轮（60s） | 9.14 | 5.61 | 0.986 | 61 | 3 |
| 第 3 轮（90s） | 9.15 | 5.61 | 0.883 | 61 | 3 |
| **平均** | **9.06** | **5.52** | **0.62** | **61** | **3** |

**结论**：工具自身**内存占用约 9 MB（私有约 5.5 MB）、CPU 平均 0.62%**，仅 3 个线程、61 个句柄。在 4 GB 内存、可用内存不足 600 MB 的高压力机器上仍保持极低开销，满足"低内存、低开销"设计目标。

### 4.2 API 延迟（端到端，每端点 5 次）

| 端点 | 最小 (ms) | 平均 (ms) | 最大 (ms) |
|---|---|---|---|
| `GET /api/v1/overview` | 19 | 21.6 | 27 |
| `GET /api/v1/processes?top=100` | 27 | 29.8 | 37 |
| `GET /api/v1/leaks` | 19 | 19.8 | 21 |
| `GET /api/v1/hotspots?top=10` | 19 | 19.8 | 23 |
| `GET /api/v1/suggestions` | 17 | 19.4 | 23 |
| `GET /api/v1/runtime` | 18 | 19.0 | 20 |
| `GET /api/v1/sampler` | 19 | 19.4 | 20 |
| `GET /`（静态首页） | 19 | 22.2 | 35 |

**结论**：各 API 端点平均延迟 **19 ~ 30 ms**，稳定且波动小。`processes` 因返回全部进程（约 145 个）相对略高，属合理。**注**：测量使用 PowerShell 客户端，包含客户端/HTTP 栈开销，服务器侧纯处理时间应更低。

### 4.3 API 吞吐（串行）

| 端点 | 请求数 | 成功数 | 总耗时 (s) | 吞吐 (req/s) |
|---|---|---|---|---|
| `GET /api/v1/overview` | 50 | 50 | 1.05 | **47.6** |
| `GET /api/v1/processes?top=100` | 50 | 50 | 1.51 | **33.1** |

**结论**：串行连续请求下约 **33 ~ 48 req/s**，全部成功（100%）。受单线程 HTTP 处理模型与 PowerShell 客户端开销限制；单连接 keep-alive 未启用（`Connection: close`），如需更高吞吐可结合并发连接使用。

## 五、测试中发现并修复的问题

性能测试过程中发现并修复了 **3 处真实缺陷**：

| # | 问题 | 影响 | 修复 |
|---|---|---|---|
| 1 | `storage.c` JSON 序列化顺序错误：`j_begin_arr` 与 `j_key("top")` 写反，输出 `["top":]` | 持久化 jsonl 与 csv 导出生成非法 JSON | 调整为 `j_key` 后 `j_begin_arr`，输出 `"top":[]` |
| 2 | `config.c` 的 `trim` 函数只移动局部指针、未原地前移，未去除前导空格 | 配置 `host = 127.0.0.1` 读成 `" 127.0.0.1"`，`inet_addr` 解析失败导致 **bind 失败、服务启动即退出** | 用 `memmove` 原地前移去除前导空白 |
| 3 | 两个编译警告（`storage.c` 路径缓冲截断、`http_server.c` 的 `#pragma comment` 在 MinGW 下被忽略） | 构建有 warning | `storage.c` 增大缓冲；`http_server.c` 加 `#ifdef _MSC_VER` 守卫 |

修复后重新构建，**编译无警告**，服务正常启动、全部端点通过。

## 六、结论

1. **低开销目标达成**：空闲 CPU 约 0.6%、内存约 9 MB、仅 3 线程，适合长期后台运行。
2. **API 响应良好**：核心端点平均延迟 19~30 ms，串行吞吐 33~48 req/s。
3. **功能完整可用**：监控、泄漏、热点、碎片、建议、报告、权限降级均验证通过。
4. **稳定性**：修复 3 处缺陷后编译零警告、服务稳定运行；未发现崩溃或资源泄漏。

### 局限与后续建议

- 本机为 **4 GB 内存、可用内存不足 600 MB** 的高压力环境，生产环境（内存更充裕）下工具自身工作集可能略有上升，CPU 与延迟预计更优。
- 延迟/吞吐测量基于 PowerShell 客户端与单线程 HTTP 模型，**绝对值不代表服务器处理极限**；如需更高吞吐，可评估为 HTTP 服务增加 keep-alive 或并发处理。
- 建议在内存充足、多核的机器上复测，以建立更完整的基线。
